# 项目背景与来龙去脉

> 这份文档讲清楚“这是什么、为什么做、做到哪一步了”。技术细节见仓库根目录的 `README.md` 与 `docs/architecture.md`。
> 本文为早期背景记录，功能状态和界面问题以 `docs/verification-v9.md` 为准。

---

## 一、这是什么项目

**一句话**：把微信读书网页版，改造成一台掌上游戏机上的"专属阅读 App"。

具体来说：
- **设备**：Powkiddy X35S 掌上游戏机（RK3566 芯片，1GB 内存，640×480 屏幕）
- **软件**：设备出厂系统是 AURKNIX（一个为游戏机定制的 Linux），前端是 EmulationStation 游戏列表
- **目标**：让用户能在**不碰电脑、不碰手机**的情况下，用这个掌机读自己的微信读书藏书，**全程只用游戏手柄操作**

**为什么难**：这台设备根本没有设计来上网
- 没有触屏、没有鼠标、没有实体键盘
- 原机没有 WiFi 模块（靠外接 USB 网卡才联上网）
- 只有 1GB 内存
- 系统根目录是**只读**的
- 屏幕只有 640×480，约等于 30 年前的显示器分辨率

而微信读书是一个**面向手机和电脑的现代网页应用**，它假设你有触屏或鼠标。所以这个项目的本质是：**在极其受限的硬件上，用软件手段"造"出一套适合手柄的交互方式**。

---

## 二、为什么做这个（用户的动机）

用户是微信读书的重度使用者，同时拥有一台掌机。核心诉求是：**想在掌机上看书，而不是额外带一台设备**。

用户的原话诉求（按时间顺序）：
1. 「把微信读书做到掌机上，登我自己的账号，读我自己的书」
2. 「全程手柄操作，不要触屏不要鼠标」
3. 「精简一下系统，别太卡」
4. 「界面要像一个 App，不要看着像网页」← **当前未完全满足的诉求**

## 三、做了什么（技术方案概览）

### 3.1 核心思路

浏览器 + 扩展 + 手柄映射，三层拼成一个"App"：

```
微信读书网页版
    ↓ 用 Chromium 以「应用模式」打开（去掉地址栏、标签页，看起来像个独立应用）
Chromium --app
    ↓ 注入一个自写扩展，负责把网页"改造"成适合手柄的样子
扩展（content.js + shell.css）
    ↓ 手柄按键通过 gptokeyb 翻译成键盘按键，扩展把它翻译成页面内的焦点导航
游戏手柄
```

### 3.2 关键决策与理由

| 决策 | 理由 |
|---|---|
| 用 **ungoogled-chromium**（不是原版 Chrome） | 开源、可裁剪、无 Google 服务拖累；arm64 便携版 |
| 用 **`--app` 模式** | 去掉地址栏/标签页/书签栏，视觉上最接近原生 App |
| 用 **扩展**（而非改网站） | 不碰站方代码，站方更新也不容易坏；只做"外壳" |
| 用 **手柄→键盘映射**（而非模拟鼠标） | 网页天生支持键盘操作，这条路最稳 |
| **硬件加速**（Mali-G52 + Vulkan） | 1GB 内存的机器，软渲染会卡死 |
| 内核**精简 236MB** | TF 卡空间与内存都紧张 |

### 3.3 交互设计（手柄能做所有事）

因为掌机没有触屏，所有操作都要用十字键 + 几个按钮完成：

- **移动焦点**：十字键（扩展实现了网格导航算法，像遥控器选电视节目那样）
- **确定/返回**：A / B
- **翻页**：L1/R1 或方向键
- **唤出菜单**：START（自绘的掌机菜单：目录/设置/搜索/上一页/书架/退出）
- **搜索**：自绘屏幕键盘（掌机没键盘，用十字键选字母拼拼音）
- **退出**：START+SELECT 同时按

### 3.4 交付物（当前状态）

**已经在掌机上运行的东西**：
- `/storage/roms/ports/Weread.sh` —— ES 游戏列表里的入口
- `/storage/roms/ports/weread/node.sh` —— 启动器（含 3 个自愈守卫）
- `/storage/.config/weread-ext/` —— 扩展（交互核心 + 视觉）
- `/storage/roms/ports/browser/` —— Chromium + 手柄映射 + 调试工具

**功能完成度**：23 项功能回归测试**全部通过**（开书、翻页、菜单、搜索、返回、退出、自愈……）。

## 四、当前的问题（用户为什么不满意）

> **用户的反馈**：「UI 界面还是不像那个 APP 端啊，看着还像个网页，你还能优化吗」

**已经做了一轮优化（v6）**，但用户仍不满意。已做的：
- 隐藏了网页标题栏、App 推广条、桌面滚动条
- 顶部大 tab 改成圆角胶囊
- 书封加圆角投影、底色改暖纸灰
- 启动直接进书架页

**为什么还是"像网页"**（我的分析）：
1. 底层还是**站方的 H5 页面**，很多细节（间距、字体、图标、加载态、点击反馈）都是网页的调性
2. 顶部导航条、书架卡片等是扩展"覆盖"上去的，**不是重新设计的**
3. 加载时是**白屏 20-30 秒**，没有启动画面
4. 阅读器内的工具栏仍是站方原样

## 五、给接手方（Claude）的核心提示

如果你想**真正做出"App 感"**，我的建议是：

### ⚠️ 最重要的约束（先看这个）

1. **正文是 canvas 绘制的**，站方 JS 会读取容器样式来算分页。
   ⇒ **绝对不能改** `.readerChapterContent` / `.preRenderContent` 的 `width`/`padding`/`font-size`/`line-height` 等布局属性，**一改就文字重叠**。
   ⇒ 所有 UI 优化只能在**非正文区域**做。

2. **`body` 背景不能全局改**，会污染阅读器的阅读主题（深色/护眼/纸色）。必须限定 `body.wr-hh-has-nav`。

3. **改完必须验证 canvas 分页没坏**（比对 `canvas.toDataURL()` 哈希）。

### 三个方向（按工作量从小到大）

**方向 A（小）**：继续"视觉打磨"
把导航条、书架卡片、按钮的样式做得更精致——更柔的阴影、更准的圆角、更好的间距、加载态。

**方向 B（中）**：重绘站方 UI 组件
比如阅读器的顶部/底部工具栏，用扩展重画成 App 风格（**注意不能碰 canvas 正文**）。

**方向 C（大，最彻底）**：自绘整个"App 首页"
完全绕开站方的 H5 首页，用扩展拉取书架数据，自己画一个 App 风格的首页（封面网格 + 最近阅读 + 分类）。这是"最像 App"的做法。

## 六、环境访问方式

- 掌机与开发机处于同一网络，通过 SSH 部署；凭据只放在本机环境变量中，不提交到仓库
- 调试：Chromium 的 CDP 端口默认只监听设备本机，需要通过 SSH 在设备上访问
- 调试：Chromium 开了 CDP 端口 `9222`（仅监听本机，需通过 SSH 在掌机上本地访问）
- ⚠️ 掌机上**绝不能跑 `find /storage`**（116GB exFAT 分区，必然超时）

详细部署与调试方法见 `docs/architecture.md`。

## 七、一句话总结

**这是一个"用软件把一个挑剔的现代网页，改造成在 1GB 内存掌机上用手柄舒服使用的 App"的项目。功能已经全部打通，剩下的核心挑战是——让它看起来真正像一个原生 App，而不是一个被修饰过的网页。**
